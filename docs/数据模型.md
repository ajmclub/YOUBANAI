# 游伴 AI · 数据模型

> **定位说明**：本文是「游伴 AI」数据库的完整说明，逐表列出字段、类型、约束与外键关系，并给出 ER 关系图、枚举字典与关键设计决策。全部内容取自 `app/schema.sql`（唯一事实来源）与 `app/config.py`，不含未落库的设想字段。

- 结构来源：`app/schema.sql`
- 数据访问层：`app/db.py`
- 种子数据：`app/seed_data.py`、`app/seed.py`
- 接口契约：`docs/API.md`

**数据库**：SQLite（单文件 `data/youban.db`），`PRAGMA foreign_keys = ON`，所有时间字段统一 `'YYYY-MM-DD HH:MM'` 文本格式。

**表总数：26 张**（`CREATE TABLE` 语句数 26），另含 8 个显式索引。分组如下：

| 分组 | 表 | 数量 |
|---|---|---|
| 景区与 IP | `parks` `characters` `skus` `activation_codes` `cooperations` | 5 |
| 用户与设备 | `users` `user_growth` `devices` | 3 |
| 剧本内容 | `scenarios` `chapters` `nodes` `node_links` `tasks` | 5 |
| 成长与进度 | `badges` `user_badges` `wardrobe_items` `user_items` `progress` `node_visits` `task_submissions` | 7 |
| 素材与 AI | `materials` `ai_jobs` | 2 |
| 运营数据 | `events` `metrics_daily` `revenue` `revenue_shares` | 4 |
| **合计** | | **26** |

> **第二轮（家长模式 + 可观测性 + 两个新剧本）没有新增任何表，也没有新增索引。**
> - 新增的《雨林寻踪》《园林谜题》复用 `scenarios` / `chapters` / `nodes` / `node_links` / `tasks`；
> - 家长模式是**只读**的派生视图，完全由现有 7 张表（`progress` / `node_visits` /
>   `task_submissions` / `user_badges` / `user_growth` / `materials` / `tasks`）联合推导；
> - 可观测性的请求指标保存在**进程内存**（`app/observability.py` 的模块级字典），业务计数实时查库，
>   两者都不落表。
>
> 表数与索引数由 `tests/final_audit.py` 的「数据库结构」一组断言守护
> （`schema.sql` 的 `CREATE TABLE` 语句数 == 运行库实际表数）。

## 1. 景区与 IP

### 1.1 `parks` 景区

**用途**：景区基础信息、景区级地理围栏半径、天气文案、探索地图坐标、点亮状态与商务模式。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 景区 ID |
| `name` | TEXT | NOT NULL | 例：`西安 · 大唐不夜城` |
| `city` | TEXT | NOT NULL | 例：`西安` |
| `lat` | REAL | — | 纬度（真实地标坐标） |
| `lng` | REAL | — | 经度 |
| `radius_m` | INTEGER | DEFAULT 1500 | 景区级地理围栏半径（米） |
| `emoji` | TEXT | DEFAULT '🏯' | 地图与卡片图标 |
| `weather` | TEXT | DEFAULT '晴 24°' | 天气文案 |
| `tip` | TEXT | DEFAULT '宜出行冒险' | 出行提示 |
| `verified` | INTEGER | DEFAULT 1 | 是否已认证 |
| `partner_mode` | TEXT | DEFAULT '内容制作 + 运营分成' | 合作模式 |
| `map_x` | REAL | DEFAULT 50 | 探索页中国地图百分比 X |
| `map_y` | REAL | DEFAULT 50 | 探索页中国地图百分比 Y |
| `lit` | INTEGER | DEFAULT 0 | 是否已点亮 |
| `sort_order` | INTEGER | DEFAULT 0 | 展示顺序 |
| `created_at` | TEXT | — | 创建时间 |

**外键**：无（根表）。
**种子数据**：12 条真实景区（见 `docs/产品设计说明书.md` 与 `tests/_inspect.txt`）。

### 1.2 `characters` 潮玩角色 / IP

**用途**：IP 主体「阿游」的定位与可装扮能力描述。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 角色 ID |
| `name` | TEXT | NOT NULL | `阿游` |
| `positioning` | TEXT | — | `儿童 AI 旅行伙伴` |
| `dressable` | TEXT | — | `城市服装 / 探险装备` |
| `avatar_emoji` | TEXT | DEFAULT '🧭' | 头像图标 |
| `tagline` | TEXT | — | `带着它，去发现世界。` |

**外键**：无。
**被引用**：`skus.character_id`。

### 1.3 `skus` 潮玩 SKU

**用途**：城市限定款与基础款的库存、激活量、售价与上架状态。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | SKU ID |
| `name` | TEXT | NOT NULL | 例：`阿游 · 大唐限定款` |
| `character_id` | INTEGER | REFERENCES `characters(id)` | 所属角色 |
| `park_id` | INTEGER | REFERENCES `parks(id)` | 关联景区（基础款为 NULL） |
| `city` | TEXT | — | 城市（基础款为 `全国`） |
| `emoji` | TEXT | — | 图标 |
| `stock` | INTEGER | DEFAULT 0 | 库存 |
| `activated` | INTEGER | DEFAULT 0 | 累计激活量 |
| `status` | TEXT | DEFAULT 'onsale' | `onsale` / `low` / `unlisted` |
| `price` | REAL | DEFAULT 399 | 售价（元） |
| `sort_order` | INTEGER | DEFAULT 0 | 展示顺序 |

**外键**：→ `characters(id)`、→ `parks(id)`。
**种子数据**：6 款（大唐 3240/28610、皇家 1860/21340、西湖 2410/18220、熊猫 980/15470 low、飞天 0/0 unlisted、基础款 8620/44960）。

### 1.4 `activation_codes` 激活码

**用途**：实体潮玩包装内的唯一激活码，是「实体 → 数字身份」的入口凭证。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `code` | TEXT | **UNIQUE** NOT NULL | 例：`YB-XA-2026-0001` |
| `sku_id` | INTEGER | REFERENCES `skus(id)` | 关联 SKU |
| `used` | INTEGER | DEFAULT 0 | 是否已使用 |
| `user_id` | INTEGER | — | 使用者（激活后写入） |
| `used_at` | TEXT | — | 激活时间 |

**外键**：→ `skus(id)`；`user_id` 为逻辑外键（无 FK 约束）。
**被引用**：`devices.code` → `activation_codes(code)`。
**种子数据**：5 条（`YB-XA-2026-0001` 已使用，`YB-BJ-2026-0002`、`YB-HZ-2026-0003`、`YB-CD-2026-0004`、`YB-BASE-2026-0005` 未使用）。

### 1.5 `cooperations` IP 联名合作

**用途**：景区与政府/文旅集团/博物馆/文创品牌的合作记录。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `park_id` | INTEGER | REFERENCES `parks(id)` | 所属景区 |
| `name` | TEXT | NOT NULL | 合作方名称 |
| `type` | TEXT | — | `IP 联名` / `内容制作 + 运营分成` / `内容授权` |
| `status` | TEXT | DEFAULT 'active' | `active` / `negotiating` / `ended` |
| `since` | TEXT | — | 起始年月，例 `2026-03` |
| `amount` | REAL | DEFAULT 0 | 合作金额 |

**外键**：→ `parks(id)`。
**种子数据**：4 条（西安文旅集团 ¥1,200,000；大唐不夜城运营公司 ¥860,000；陕西历史博物馆 洽谈中；故宫文创 ¥2,400,000）。

## 2. 用户与设备

### 2.1 `users` 用户 / 家庭

**用途**：孩子/家庭账号的数字身份。注意：`level` 与 `growth_total` 都冗余存库，但**读取时以 `growth_total` 实时反推等级**（`utils.level_of()`）。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 用户 ID |
| `nickname` | TEXT | NOT NULL | 例：`小小探险家` |
| `family_name` | TEXT | — | 例：`小小探险家 · 王家` |
| `avatar` | TEXT | DEFAULT '🧭' | 头像 emoji |
| `city` | TEXT | DEFAULT '西安' | 所在城市 |
| `level` | INTEGER | DEFAULT 1 | 等级（写库缓存，前端展示以反推为准） |
| `growth_total` | INTEGER | DEFAULT 0 | 成长值总和 |
| `travel_days` | INTEGER | DEFAULT 12 | 旅行天数 |
| `age_band` | TEXT | DEFAULT '8-12' | 年龄层 |
| `created_at` | TEXT | — | 创建时间 |
| `last_active` | TEXT | — | 最后活跃时间 |

**外键**：无。
**被引用**：`user_growth`、`devices`、`user_badges`、`user_items`、`progress`、`node_visits`、`task_submissions`。

### 2.2 `user_growth` 成长五维度

**用途**：按维度存用户的成长值累计。复合主键天然保证「一个用户一个维度一行」。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `user_id` | INTEGER | NOT NULL REFERENCES `users(id)`，**PK** | 用户 |
| `dim` | TEXT | NOT NULL，**PK** | `explore` / `create` / `observe` / `knowledge` / `courage` |
| `value` | INTEGER | DEFAULT 0 | 该维度累计值 |

**外键**：→ `users(id)`；主键 `(user_id, dim)`。
**种子数据**：6 用户 × 5 维 = 30 行；演示用户 `{explore:78, create:62, observe:85, knowledge:70, courage:66}`（合计 361）。

### 2.3 `devices` 潮玩设备

**用途**：已激活的实体潮玩实例——伙伴昵称、当前装扮、在线状态。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `code` | TEXT | REFERENCES `activation_codes(code)` | 激活码（业务唯一键） |
| `sku_id` | INTEGER | REFERENCES `skus(id)` | 所属 SKU |
| `user_id` | INTEGER | REFERENCES `users(id)` | 归属用户 |
| `nickname` | TEXT | DEFAULT '阿游' | 孩子给伙伴取的名字 |
| `outfit` | TEXT | — | 当前装扮名，例 `大唐限定装扮` |
| `status` | TEXT | DEFAULT 'activated' | `activated` / `online` / `offline` |
| `online` | INTEGER | DEFAULT 1 | 在线标记 |
| `activated_at` | TEXT | — | 激活时间 |

**外键**：→ `activation_codes(code)`、→ `skus(id)`、→ `users(id)`。
**种子数据**：2 台（`YB-XA-2026-0001` 阿游 / 大唐限定装扮；`YB-BJ-2026-0002` 星仔 / 皇家限定装扮）。

**外键**：→ `scenarios(id)`，级联删除。
**被引用**：`nodes.chapter_id`。
**种子数据**：31 章（大唐密令 5、西湖奇缘 4、熊猫调查局 5、皇家秘境 3、飞天密码 2、苗岭宝藏 4、雨林寻踪 4、园林谜题 4）。

### 3.3 `nodes` 剧情节点（STORY NODE）

**用途**：景区内可被触发的剧情点，承载坐标、围栏半径、剧情文案与阿游台词。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `scenario_id` | INTEGER | NOT NULL REFERENCES `scenarios(id)` **ON DELETE CASCADE** | 所属剧本 |
| `chapter_id` | INTEGER | REFERENCES `chapters(id)` **ON DELETE SET NULL** | 所属章节 |
| `idx` | INTEGER | DEFAULT 1 | 节点序号（决定解锁顺序） |
| `name` | TEXT | NOT NULL | 节点名 |
| `kind` | TEXT | DEFAULT 'main' | `entry` / `main` / `branch` / `reward` |
| `trigger_type` | TEXT | DEFAULT 'gps' | `gps` / `qr` / `nfc` / `prev` |
| `lat` | REAL | — | 纬度 |
| `lng` | REAL | — | 经度 |
| `radius_m` | INTEGER | DEFAULT 40 | 节点围栏半径（米） |
| `age_band` | TEXT | DEFAULT '8-12' | 年龄层 |
| `place` | TEXT | — | 具体地点，例 `大雁塔` |
| `story_text` | TEXT | — | 剧情文案 |
| `ai_dialog` | TEXT | — | 阿游对孩子说的话 |
| `hint` | TEXT | — | 提示 |
| `reward_badge_id` | INTEGER | — | 节点奖励徽章（逻辑外键 → `badges(id)`） |
| `x` | REAL | DEFAULT 100 | 编辑器画布 X |
| `y` | REAL | DEFAULT 170 | 编辑器画布 Y |
| `sort_order` | INTEGER | DEFAULT 0 | 排序 |

**外键**：→ `scenarios(id)` 级联删除、→ `chapters(id)` 置空。
**被引用**：`tasks.node_id`、`node_visits.node_id`、`node_links.from_node/to_node`。
**种子数据**：51 个节点（按剧本：大唐密令 10、西湖奇缘 5、熊猫调查局 6、皇家秘境 5、飞天密码 4、苗岭宝藏 7、雨林寻踪 7、园林谜题 7）。
以《大唐密令》为例：10 节点，其中 `entry` 1 / `main` 6 / `branch` 2 / `reward` 1。

> ⚠️ **已知数据缺陷（未修复）**：节点 `#14`（`scenario_id=2`《西湖奇缘》，`idx=4`
> 「数一数三潭印月的月亮」）的 `kind = 'find'`，**不在合法枚举内**
> （`NODE_KINDS` 只有 `entry` / `main` / `branch` / `reward`）。
> 这应该是把任务类型 `find` 误写到了 `kind` 字段上，正确值应为 `branch`（与同剧本 `idx=3` 的支线节点一致）。
>
> 影响是**静默降级**而非报错：`utils.node_kind_label()` 对未知 kind 回退为 `'STORY NODE'`
> （`NODE_KINDS.get(kind, "STORY NODE")`），因此该节点在 C 端节点页与 B 端编辑器里
> 显示为通用「STORY NODE」，而不是「BRANCH · 支线」。B 端热度榜的同名映射也会回退为「剧情点」。
>
> 全库 kind 实际分布：`main` 23 / `branch` 11 / `entry` 8 / `reward` 8 / **`find` 1**。
> 五套自动化验证目前**没有覆盖 kind 枚举合法性**，因此全部通过却漏掉了它——建议补一条种子数据
> 校验断言（`kind ∈ NODE_KINDS`、`trigger_type ∈ {gps,qr,nfc,prev}`、`verify_mode ∈ {auto,answer,keyword,photo}`）。

### 3.4 `node_links` 剧情连线

**用途**：编辑器画布上的有向连线（含颜色），仅用于可视化编排。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `scenario_id` | INTEGER | NOT NULL REFERENCES `scenarios(id)` **ON DELETE CASCADE** | 所属剧本 |
| `from_node` | INTEGER | NOT NULL | 起点节点（逻辑外键 → `nodes(id)`） |
| `to_node` | INTEGER | NOT NULL | 终点节点（逻辑外键 → `nodes(id)`） |

**种子数据**：《大唐密令》10 条连线，例如 `(1,2,gold) (5,6,purple) (10,7,forest)`。

| `desc` | TEXT | — | 任务描述（对孩子说的话） |

## 4. 成长与进度

### 4.1 `badges` 徽章

**用途**：徽章定义（含城市、关联剧本、稀有度）。

| 字段 | 类型 | 约束 / 默认 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | — |
| `name` | TEXT | NOT NULL | 例：`大唐探索家` |
| `emoji` | TEXT | — | 图标 |
| `city` | TEXT | — | 归属城市 |
| `scenario_id` | INTEGER | REFERENCES `scenarios(id)` **ON DELETE SET NULL** | 关联剧本 |
| `rarity` | TEXT | DEFAULT 'common' | `common` / `rare` / `legend` |

> 这是实现家长模式时实际踩到的坑，详见 9.7 节。

## 9. 关键设计决策

### 9.1 `node_visits` 的 `UNIQUE(user_id, node_id)` 实现「首次到访」

```sql
CREATE TABLE node_visits (
  ...
  UNIQUE (user_id, node_id)
);
```

- `growth.ensure_visit()` 先 `SELECT 1 ... WHERE user_id=? AND node_id=?`，存在返回 `False`，不存在则 `INSERT` 并返回 `True`；
- `POST /api/c/locate` 用这个布尔值决定是否写 `events`（只在首次到访时产生「{昵称} 到达了「{节点名}」」动态），避免同一节点反复刷动态；
- 带来的产品语义：`node_visits` 是**到访集合**而不是日志流；需要「到访次数」时应另建事件表或统计 `events`。
- 唯一约束同时兼作 `(user_id, node_id)` 查询索引。

### 9.2 `progress` 的 `UNIQUE(user_id, scenario_id)` 实现单条进度

```sql
UNIQUE (user_id, scenario_id)
```

- `growth._refresh_progress()` 采用「先查后写」：存在 `UPDATE`，不存在 `INSERT`；
- 产品语义：一个用户在一个剧本只有一条进度记录，`chapter_idx / percent / status` 是**快照**而不是历史；
- 剧本完成（`status='done'`）时顺带补发该剧本徽章，避免「完成但没拿到徽章」。

### 9.3 `task_submissions` 用行数累计 `target_count`

计数型任务（例如「在不夜城找回三枚古铜钱」`target_count = 3`）不新增字段，而是**每通过一次写一行**：

```sql
SELECT COUNT(*) FROM task_submissions WHERE user_id = ? AND task_id = ? AND passed = 1
```

优点：

1. 进度与原始作答天然绑定，可回溯「找到的是哪三枚」（`photo_note` 逐条保存）；
2. 不必维护额外的计数器字段，也就不会出现计数器与记录不一致；
3. 未通过的行同样写库（`passed = 0`），保留了「试错过程」这一教育数据。

代价：需要 `idx_subs_user (user_id, task_id)` 支撑计数查询。

### 9.4 `ai_jobs.result_json` 裁剪落库

`story_engine._shrink()` 只保存必要字段：

```python
{
  "engine", "mode",
  "worldview": (≤ 2000 字),
  "scenario", "chapters",
  "node_count": len(nodes),      # 只存数量，不存完整节点
  "rewards", "elapsed_ms"
}
```

原因：一次 `full` 生成会产出 8~12 个节点的完整文案（每个节点含故事、台词、提示、任务描述），完整结果可达数十 KB；而落库生成结果时**真正的产物是已入库的草稿剧本**（`created_scenario_id`），`result_json` 只需要保留「这次生成长什么样」的审计快照。裁剪后既保留了生成历史页要展示的字段，又避免 `ai_jobs` 随生成次数线性膨胀。

### 9.5 冗余字段与逻辑外键的取舍

| 设计 | 位置 | 原因 |
|---|---|---|
| `tasks.scenario_id` 冗余 | 已知 `node_id` 即可推出 | 让「按剧本聚合任务状态」一次查询完成，避免 JOIN `nodes` |
| `node_visits.scenario_id` 冗余 | 同上 | 统计剧本级到访数（`_refresh_completion_rates`）时免 JOIN |
| `task_submissions.node_id` 冗余 | 同上 | 后台轨迹按节点聚合展示 |
| `nodes.x / y` | 编辑器画布坐标 | 前端直接绝对定位，无需布局计算 |
| `parks.map_x / map_y` | 探索地图百分比坐标 | 同上 |
| `node_links.from_node / to_node` 无 FK | 连线是纯展示数据 | 允许先建连线后建节点；删除节点时由路由手工清理 |
| `users.level` 与 `user_growth` 并存 | 等级可反推 | `level` 是写库缓存便于 SQL 排序，展示层始终用 `level_of(growth_total)` 反推 |
| `scenarios.chapter_count` / `completion_rate` | 可由子表统计 | 后台列表页避免 N 次统计查询；播种时由 `_refresh_completion_rates()` 按真实到访率校正 |

### 9.6 删除行为

| 行为 | 表 |
|---|---|
| `ON DELETE CASCADE` | `chapters`、`nodes`、`tasks`、`node_links`、`progress`、`node_visits`、`task_submissions`（删剧本/节点即清空下游数据） |
| `ON DELETE SET NULL` | `nodes.chapter_id`（章被删时节点保留，避免误删章节导致剧情节点丢失）、`badges.scenario_id`（剧本删除后徽章仍保留在徽章墙） |
| 手工清理 | `admin.delete_node()` 依次删除 `node_links`（from/to）、`tasks`、`node_visits`，最后删 `nodes` |
| 重建整库 | `db.drop_all_tables()` + 重新 `executescript(schema.sql)`（`python run.py --reseed`） |

### 9.7 家长模式用到了哪些表（以及两个坑）

家长模式（`app/engines/parent.py`）**没有自己的表，也不写任何表**——
它是一组只读的派生查询。用到的表与关联方式如下：

| 输出区块 | 用到的表 | 关联方式 |
|---|---|---|
| 孩子档案 / 等级 | `users`（`growth_total` → `utils.level_of()` 反推） | 直接查 |
| 五维画像 | `user_growth` | `WHERE user_id = ?` |
| 概览：走过的城市 | `progress` ⋈ `scenarios` | `COUNT(DISTINCT scenarios.park_id)` |
| 概览：完成的剧本 | `progress` | `WHERE status = 'done'`；分母用 `scenarios WHERE status != 'draft'` |
| 概览：探索的剧情点 | `node_visits` | `COUNT(*) WHERE user_id = ?` |
| 概览：完成的任务 | `task_submissions` | `COUNT(DISTINCT task_id) WHERE passed = 1` |
| 概览：获得的徽章 | `user_badges` | `COUNT(*) WHERE user_id = ?`（分母 `badges` 总数） |
| 概览：累计时长 | `task_submissions` ⋈ `tasks` | `SUM(tasks.avg_minutes)` over 去重后的已通过任务 |
| 近 7 天活跃 | `task_submissions` | `GROUP BY substr(submitted_at,1,10)` 且 `passed = 1` |
| 近期徽章 | `user_badges` ⋈ `badges` | `ORDER BY got_at DESC LIMIT 6` |
| 进行中剧本 | `progress` ⋈ `scenarios` ⋈ `parks` | `ORDER BY updated_at DESC` |
| **建议：下一站** | `parks` ⟕ `scenarios`（`status != 'draft'`） | `WHERE parks.lit = 0 AND scenarios.id IS NOT NULL ORDER BY sort_order LIMIT 1` |
| **建议：可拿徽章** | `badges` ⋈ `scenarios`（`status = 'online'`）+ `user_badges` 反查 | `WHERE badge_id NOT IN (SELECT badge_id FROM user_badges WHERE user_id = ?)` |
| 报告：时间轴 | `node_visits` ⋈ `nodes` ＋ `task_submissions` ⋈ `tasks` | 两段各自排序后合并，再按时间整体排序 |
| 报告：本次成长累计 | `task_submissions` ⋈ `tasks` | 遍历 `growth_gain` JSON 并求和 |
| **报告：知识点反查** | `materials` + `nodes.place` | `WHERE park_id = ? AND status='indexed' AND (title LIKE ? OR tags LIKE ?)` |
| **报告：回家提问** | `task_submissions` ⋈ `tasks`、`materials` ⋈ `scenarios` | 见 `技术架构.md` 4.6 节 |
| 报告：估算时长 | `task_submissions` ⋈ `tasks` | `SUM(tasks.avg_minutes)` |
| 报告：获得的徽章 | `badges` + `user_badges` | `WHERE badges.scenario_id = ?` |

#### 坑 ①：`task_submissions` 没有 `scenario_id`

见 4.7 节的警告框。`order by`/`where` 想按剧本过滤，**必须**
`JOIN tasks t ON t.id = ts.task_id` 后用 `t.scenario_id`。
家长模式的「时间轴」「成长累计」「完成任务数」「估算时长」四处查询都踩过这个点。

#### 坑 ②：`events` 没有 `user_id`，不能用来统计用户行为

`events` 是**面向 B 端**的运营动态流，字段只有 `type` / `title` / `detail` / `park_id` / `created_at`
（见 6.1 节），**没有 `user_id`**。因此：

- 家长模式里的一切「这个孩子做了什么」都改用 `node_visits` 与 `task_submissions`；
- `observability.business_counters()` 里也**没有**基于 `events` 的用户计数，
  而是用 `COUNT(DISTINCT user_id) FROM node_visits` 得到 `users_with_trail`；
- 只有 `events_logged`（总条数，不区分用户）是可以从 `events` 直接统计的。

> 这个坑还侧面说明了一件事：C 端行为要能「按用户回溯」，就必须落在
> `node_visits` / `task_submissions` / `progress` 这三张带 `user_id` 的表上。
> 写 `events` 只是为了后台实时动态好看，不能当作行为审计数据源。
