## 1. 技术选型与理由

### 1.1 依赖清单（`requirements.txt`）

```
fastapi>=0.110
uvicorn>=0.27
pydantic>=2.6
```

除此之外**只用 Python 标准库**：`sqlite3`（数据库）、`urllib.request`（大模型 HTTP 调用）、`json`、`re`、`math`、`threading`、`datetime`、`random`。没有 ORM、没有数据库服务、没有第三方 HTTP 客户端、没有模板引擎。

### 1.2 选型理由

| 选型 | 理由 |
|---|---|
| **FastAPI** | 一份代码同时得到运行时接口与 Swagger 文档（`/docs`）；Pydantic 请求模型把 `ActivateReq`、`LocateReq`、`SubmitReq`、`GenerateReq` 等参数校验写成声明式代码；`StaticFiles` 可直接挂载原生前端，无需额外 web 服务器 |
| **SQLite（标准库 `sqlite3`）** | 单文件数据库（`data/youban.db`），随项目走，零安装零配置；演示、评审、离线环境都能一键跑起来；`PRAGMA foreign_keys` 与 `WAL` 都可用；数据量级（10²~10⁴ 行）远未到 SQLite 的瓶颈 |
| **原生 HTML / CSS / JS** | 无构建步骤：改完刷新即可见；移动端 H5 与桌面后台都用同一套 `fetch` + 模板字符串渲染；避免 `node_modules`、打包器与版本漂移 |
| **无 ORM，手写 SQL** | 表结构（26 张）本身就是产品资产，`app/schema.sql` 是唯一事实来源；统计类查询（节点热度、漏斗、完成率）用 SQL 表达比 ORM 更直观 |
| **`urllib.request` 调大模型** | 只依赖标准库，未配置大模型时**完全离线可跑**，配置后自动切换（见第 6 节） |

### 1.3 为什么不用 Node / npm

1. **运行环境**：目标环境是 Windows + PowerShell + Python 3.14，**没有 Node**。引入前端构建链会让「单命令启动」的承诺失效。
2. **交付形态**：这是一个可离线演示的完整原型，任何需要 `npm install` 的环节都会变成评审现场的风险点。
3. **能力已足够**：前端只需要「取数据 → 拼 HTML → 插进 DOM」三类操作，原生 `fetch` + `innerHTML` + 事件委托即可完成，`web/c/app.js` 与 `web/admin/app.js` 分别覆盖 5 个 C 端页面与 10 个 B 端模块。
4. **可读性优先**：原型阶段最大的成本是**沟通成本**，不是运行时性能。原生代码可以被产品、设计和后端同时读懂。

### 1.4 启动方式（三选一）

```powershell
python run.py                          # 一键启动（推荐）
python run.py --reseed                 # 重新播种演示数据
python run.py --port 8080              # 指定端口
python -m uvicorn app.main:app --port 8770
```

启动后：

| 入口 | 地址 | 说明 |
|---|---|---|
| 项目门户 | `http://127.0.0.1:8770/` | `web/index.html` |
| C 端 H5 | `http://127.0.0.1:8770/c/` | 手机端界面 |
| B 端后台 | `http://127.0.0.1:8770/admin/` | 景区运营台 |
| API 文档 | `http://127.0.0.1:8770/docs` | FastAPI 自动生成 |

服务地址与端口来自环境变量 `YOUBAN_HOST`（默认 `127.0.0.1`）与 `YOUBAN_PORT`（默认 `8770`，见 `app/config.py`）。

**端口自动回退**：`run.py` 在启动前用 `port_is_free()` 做一次真实绑定探测；若端口被占用，
则用 `find_free_port()` 向上寻找空闲端口，打印提示并以实际端口启动。

> ⚠️ 该探测**刻意不设置 `SO_REUSEADDR`**。Windows 下 `SO_REUSEADDR` 允许绑定到一个
> 已被占用的端口（语义与 Linux 不同），一旦设置，探测会永远返回「可用」，
> 而 uvicorn 随后以独占方式绑定失败（`WinError 10048`）。这是一个实测踩到的坑。

```python
def port_is_free(host: str, port: int) -> bool:
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
        try:
            s.bind((host, port))      # 注意：不设 SO_REUSEADDR
            return True
        except OSError:
            return False
```


首次启动时 `app/main.py` 的 `lifespan` 会调用 `db.init_db(force=False)`，若 `parks` 表为空（`db.is_seeded()` 为假）则自动播种并打印统计：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    db.init_db(force=False)
    if not db.is_seeded():
        stats = seed.seed_all(force=False)
        ...
```

分层约束：

- 接口层**不写业务算法**，只做参数校验、组装与 404/400 错误；
- 引擎层**不感知 HTTP**，只接收 dict、返回 dict（唯一例外是 `story_engine.generate()` 抛 `ValueError`，由路由转成 404）；
- 数据层**不写业务 SQL 语义**，只提供通用 CRUD 原语；
- 种子层是**唯一**写入初始数据的地方，`app/main.py` 与 `run.py` 都只调用 `seed.seed_all()`；
- 可观测性中间件是**唯一**的横切关注点，位于接口层之上，不侵入任何路由函数。

## 4. 六个引擎

### 4.1 `geo.py` 地理围栏引擎

| 项 | 内容 |
|---|---|
| 输入 | `parks` / `nodes` 记录（dict 列表）+ 用户经纬度 |
| 输出 | 命中景区 dict；或 `(triggered, nearby)` 两组节点（附 `distance_m` / `distance_text`） |
| 被谁调用 | `c_end.locate()`、`c_end.home()`、`chat.reply()` |

**Haversine 公式**（`EARTH_RADIUS_M = 6371000.0`）：

```python
a = sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2)
d = 2 · R · asin(√a)
```

**两级围栏**：

| 级别 | 判定 | 容差 | 作用 |
|---|---|---|---|
| 景区级 | `haversine(user, park) <= park.radius_m × 1.5` | 1.5 倍 | 先确定「用户在哪个景区」，多命中时取最近的一个 |
| 节点级 | `haversine(user, node) <= node.radius_m` | — | 进入即触发（`triggered`） |
| 节点级「附近」 | `radius_m < d <= radius_m × NEARBY_FACTOR` | `NEARBY_FACTOR = 8` | 用于「附近的故事点」「走过去看看好不好？」 |

> 倍率已提取为模块常量 `geo.NEARBY_FACTOR = 8`，docstring 与代码保持一致（早期版本 docstring 误写为「6 倍」，已修正）。

`find_park()` 会跳过 `lat`/`lng` 为空的景区，并在多个景区同时命中时返回**距离最近**的一个；`locate_nodes()` 会跳过坐标缺失的节点，并对结果按距离升序排序。

距离文案格式化：`< 1000m` → `"340m"`；否则 → `"1.2km"`。

### 4.2 `story.py` 剧情状态引擎

| 项 | 内容 |
|---|---|
| 输入 | `user_id`、`scenario_id`（或 `node` dict） |
| 输出 | 节点状态映射 / 可达节点 / 剧本详情（章节 + 节点 + 任务）/ 编辑器画布 |
| 被谁调用 | `c_end.home/explore/scenario/locate`、`admin.scenario_detail`、`admin.update_node`、`chat.reply` |

**节点三态**（`node_state`）：

| 状态 | 条件 |
|---|---|
| `done` | `growth.node_is_done()`：节点下所有启用任务都达到 `target_count`（无任务则到访即完成） |
| `active` | 未完成，但存在 `node_visits` 记录 |
| `locked` | 未完成且未到访 |

**顺序解锁算法**（`available_nodes`，本项目「前置节点解锁」规则的唯一实现）：

```python
for n in nodes:                                  # nodes 按 idx 升序
    if growth.node_is_done(user_id, n["id"]):
        continue                                 # 已完成不再触发
    prev = SELECT id FROM nodes WHERE scenario_id = ? AND idx < ?
    if all(growth.node_is_done(user_id, p["id"]) for p in prev):
        out.append(n)                            # 所有前置完成 → 可达
```

`locked_reason()` 返回第一条未完成的前置节点名，供前端提示「需要先完成「神秘来信」」。

**章节状态推导**（`scenario_detail`）：

| 章节状态 | 条件 |
|---|---|
| `done` | 该章所有节点 `done` |
| `now` | 该章存在 `done` 或 `active` 节点 |
| `todo` | 其余情况 |

**进度计算**：`visited = 未处于 locked 的节点数`，`percent = round(visited × 100 / total_nodes)`；`current_node` 取**第一个非 done 的节点**（全部完成时取最后一个节点）。

**性能设计**：`node_status_chain()` 一次性把整章所有节点状态算完（先把该用户的 `node_visits` 与按任务聚合的 `passed` 计数各查一次），避免逐节点 N+1 查询。

编辑器画布 `scenario_canvas()` 以**演示用户（user_id = 1）** 的进度渲染 `done/active` 标记，用于后台可视化编排。

### 4.3 `growth.py` 判定与成长引擎

| 项 | 内容 |
|---|---|
| 输入 | `task` dict + `payload {answer, photo_note}` |
| 输出 | 判定结果、反馈文案、成长增量、总成长值、升级信息、徽章、节点完成标记、下一节点 |
| 被谁调用 | `c_end.submit_task()`、`story.py`（状态判定）、`c_end.locate()`（首次到访） |

**四种判定算法**（`judge()` 的完整分支）：

```python
mode = task["verify_mode"] or "keyword"

if mode == "auto":                       # 到达即过
    return True, FEEDBACK_OK[0], "已到达"

if mode == "photo":                      # photo_note 非空即过
    if photo_note.strip():
        return True, "拍得真好！阿游把你的照片收进故事里了 📷", photo_note.strip()
    return False, "还没有拍下照片哦，先找到目标再按快门～", raw

user = strip().lower() 去掉半角/全角空格
if not user:
    return False, "还没有填写答案哦～", raw

expected = _norm(task["answer"])
keywords = task["keywords"].split(",")

if mode == "answer":                     # 精确匹配 或 命中关键词之一
    if user == expected or user in [_norm(k) for k in keywords]:
        return True, FEEDBACK_OK[1], raw
    return False, FEEDBACK_FAIL[0], raw

# 默认 keyword：answer 或任一关键词「包含于」用户输入
for p in [expected] + [_norm(k) for k in keywords]:
    if p and p in user:
        return True, FEEDBACK_OK[0], raw
return False, FEEDBACK_FAIL[1], raw
```

**保底成长值 20%**（`FAIL_RATIO = 0.2`）：

```python
def fail_gain(task):
    for dim, val in json_loads(task["reward_growth"]).items():
        out[dim] = max(1, round(val * 0.2))     # 每维至少 1 点
    if not out:
        out = {"courage": 1}                    # 任务无奖励配置时的兜底
```

实测：任务「按正确顺序排列四条线索」奖励为 `{knowledge:16, courage:10, create:6}`，答错时得到 `{knowledge:3, courage:2, create:1}`，反馈里显示「+6」（`tests/_report.txt` 的 `submit 错误答案 … +6`）。

**计数型任务**：`task_done_count()` = `COUNT(*) FROM task_submissions WHERE user_id=? AND task_id=? AND passed=1`；`submit()` 开头若 `already >= target` 则直接返回完成态（不重复发成长值）。

**节点完成**：`node_is_done()` = 节点下**所有** `enabled=1` 任务都 `task_is_complete()`；节点无任务时退化为「到访即完成」。

**等级反推**：`utils.level_of(growth_total)` 遍历 `LEVEL_THRESHOLDS`，取 `growth_total >= threshold` 的最大下标 +1，并以 `len(LEVEL_NAMES) = 10` 封顶；`add_growth()` 每次写入 `growth_total` 与 `level` 两个字段。

**徽章三级解锁优先级**（`_try_unlock_badge()`）：

1. `tasks.reward_badge_id`
2. `nodes.reward_badge_id`
3. 若该剧本 `kind='reward'` 的结算节点已完成 → 取 `badges.scenario_id = sid ORDER BY id LIMIT 1`

此外 `_refresh_progress()` 在剧本 `status='done'` 时也会补发剧本徽章。`grant_badge()` 幂等：已拥有直接返回 `None`。

**进度刷新**（`_refresh_progress()`）：`percent = round(visited × 100 / total)`；`status = 'done' if visited >= total else 'ongoing'`；`chapter_idx` 取「已到访节点中 idx 最大者所属章节」；存在则 `UPDATE`，不存在则 `INSERT`（受 `UNIQUE(user_id, scenario_id)` 保护）。

**`submit()` 的副作用链**：写 `task_submissions` → 累加成长值 → 判定升级 → 确保 `node_visits` 存在（`source='task'`）→ 尝试解锁徽章 → 若节点完成则刷新 `progress` → 返回 `next_node`。

### 4.4 `chat.py` 对话引擎

| 项 | 内容 |
|---|---|
| 输入 | `user`、`device`、`text`、`lat/lng`、`history` |
| 输出 | `intent`、`messages[]`、`quest_card`、`suggestions[]`、`park` |
| 被谁调用 | `c_end.chat()` |

**六种意图识别**（`_detect_intent()`，纯正则、可读、可测，另有 `empty` 兜底）：

| 意图 | 正则 | 命中后的行为 |
|---|---|---|
| `nearby` | `附近\|周围\|还有什么\|哪里\|哪儿\|下一个` | 有 `triggered` 节点 → 「就在旁边！…离我们只有 N 米」+ 任务卡；否则给 `nearby` 节点距离；否则给出「换一座城市」建议 |
| `tired` | `累\|休息\|走不动\|饿\|渴\|不想` | 从 `TIRED_REPLIES` 按 `len(text) % 2` 轮换 |
| `knowledge` | `讲讲\|介绍\|为什么\|是什么\|历史\|知识\|说说` | 命中 `KNOWLEDGE_HINTS` 关键词 → 检索素材回答；否则用本景区最长素材兜底 |
| `accept` | `好呀\|好的\|接受\|这就去\|我去\|开始\|出发\|嗯` | 「太棒啦！那我们开始吧——{节点名}」+ 任务卡 |
| `greeting` | `你好\|嗨\|hi\|hello\|在吗\|阿游`（忽略大小写） | 从 `GREETING_REPLIES` 按 `len(text) % 3` 轮换 |
| `chat` | 以上都不命中 | 尽量结合当前节点：追加 `ai_dialog` 与「（节点名 · 距离m）」+ 任务卡 |

`empty`（空输入）→ 「我一直在这儿呢，随时可以出发～」。

**素材检索回答**（`_material_answer()`）：

```sql
SELECT title, content FROM materials
WHERE status = 'indexed' AND (title LIKE ? OR tags LIKE ? OR content LIKE ?)
ORDER BY LENGTH(content) ASC LIMIT 1
```

取**内容最短**的一条（更可能是针对性条目），再按 `。！？` 切句取前 2 句、截断到 160 字，包成「好呀，我给你讲讲「标题」——…」。这样既保证内容来自景区资料，又保证一次不给孩子太多信息。

**位置上下文**：与 `POST /api/c/locate` 共用同一套规则——先 `find_park()`，再对每个景区取 `available_nodes()`，最后 `locate_nodes()`。因此对话里推荐的故事点与定位触发的结果**永远一致**。

**大模型可选**：`_llm_reply()` 在 `LLM_ENABLED` 时优先调用，失败（`URLError/HTTPError/KeyError/ValueError/TimeoutError/OSError`）静默返回 `None`，自动退回规则回复，不阻断对话。

`KNOWLEDGE_HINTS` 当前覆盖 8 个关键词：大雁塔 / 塔 / 钟楼 / 城墙 / 博物馆 / 铜钱 / 飞天 / 熊猫。

### 4.5 `story_engine.py` AI Story Engine

| 项 | 内容 |
|---|---|
| 输入 | `park_id`、`mode`、`age_band`、`style`、`scenario_title`、`chapter_count`、`node_count`、`persist` |
| 输出 | `engine`、`worldview`、`scenario`、`chapters`、`nodes`（含 `task`）、`rewards`、`sources`、`notes`、`elapsed_ms`、`job_id`、`created_scenario_id` |
| 被谁调用 | `admin.ai_generate()`、`admin.ai_engine()`（能力信息） |

**离线规则引擎的生成流程**（`_offline_generate()`）：

```
① 素材读取      load_materials(park_id, limit=240)
                优先本景区 status='indexed'；不足 20 条时用其他景区素材补齐
② 世界观        取 architecture / history / legend / nature / heritage 各一条
                拼装：年龄层世界观前缀 + 景区名 + 建筑题名与摘要 + 历史题名与摘要
                     + 传说题名 + 故事基调 + 年龄层叙事要求
③ 章节模板      CHAPTER_TEMPLATES（8 条）按 i % 8 轮转，{place}/{anchor}/{nature} 占位
                chapter_count 钳制到 [1, 12]
④ 八点节点结构  NODE_STRUCTURE（入口/古建筑/古树/博物馆/山谷/观景台/隐藏地点/终极任务）
                按 i % 8 轮转；最后一个节点强制 kind='reward'，标题改为年龄层奖励名
                节点坐标 = 景区坐标 + _jitter 抖动（12 个偏移量，约 ±0.004° ≈ 400m）
                半径 = 40 + (i % 3) × 10 米
⑤ 任务轮转      TASK_CYCLE = [observe, find, photo, solve] 按 i % 4 轮转
                photo 类型 → verify_mode='photo'；其余 → 'keyword'
                find 类型 → target_count=3；其余 → 1
                关键词取自该节点来源素材的 tags（最多 6 个），answer = 第一个 tag
⑥ 奖励          AGE_PLAY 的年龄层奖励 + 「{城市}记忆」+「连环解密者」；
                若存在 heritage 素材，额外加一条「{遗产名}传承人」徽章
⑦ 来源溯源      sources[] = 实际被引用的素材 (material_id, title, category)，最多 12 条
⑧ 落库          mode='full' 且 persist=True → persist_scenario()
                ai_jobs 记录（含裁剪后的 result_json）
```

**节点结构 ↔ 素材分类映射**（`category_map`），保证每个节点都有资料支撑：

| 结构 | 入口 | 古建筑 | 古树 | 博物馆 | 山谷 | 观景台 | 隐藏地点 | 终极任务 |
|---|---|---|---|---|---|---|---|---|
| 素材分类 | `geo` | `architecture` | `nature` | `heritage` | `nature` | `geo` | `legend` | `history` |

**奖励按年龄层缩放**（`_reward_for()`）：

| 任务类型 | 基础奖励 | 4-8（×1.0） | 8-12（×1.3） | 12+（×1.6） |
|---|---|---|---|---|
| `observe` | `{observe:10, knowledge:5}` | 10 / 5 | 13 / 6 | 16 / 8 |
| `find` | `{explore:12, observe:6}` | 12 / 6 | 16 / 8 | 19 / 10 |
| `photo` | `{create:12, observe:6}` | 12 / 6 | 16 / 8 | 19 / 10 |
| `solve` | `{knowledge:14, courage:8}` | 14 / 8 | 18 / 10 | 22 / 13 |

**模式裁剪**（同一份生成结果按 `mode` 置空无关字段）：

| mode | 处理 |
|---|---|
| `mainline` | `nodes = None`、`rewards = None` |
| `task` | `worldview = None`、`chapters = None`、`rewards = None`；`nodes` 仅保留 `name/kind/task` |
| `dialog` | `worldview = None`、`chapters = None`、`rewards = None`；`nodes` 仅保留 `name/ai_dialog/story_text/hint` |
| `reward` | `worldview/chapters/nodes = None` |
| `full` | 全部字段；`persist=True` 时落库为 `draft` 剧本 |

**`persist_scenario()` 落库顺序**（`scenarios` → `chapters` → `badges` → `nodes` → `tasks` → `node_links`）：

- 剧本 `status='draft'`、`source='ai'`；
- 节点按 `i * n_ch // len(nodes)` 均匀映射到章节；
- `kind='reward'` 的节点挂上第一枚奖励徽章（`reward_badge_id`）；
- 画布坐标自动布局：`x = 12 + (i % 3) * 180`、`y = 170 + (i // 3) * 130`（每行 3 个）；
- 节点之间顺序连线（`color='gold'`）。

**`ai_jobs.result_json` 裁剪**（`_shrink()`）只保留 `engine`、`mode`、`worldview`（截断 2000 字）、`scenario`、`chapters`、`node_count`、`rewards`、`elapsed_ms`，避免生成历史把库撑大。

**大模型分支与自动回退**（`generate()`）：

```python
if LLM_ENABLED:
    try:
        result = _llm_generate(...)      # OpenAI 兼容 /chat/completions
        engine_used = ENGINE_LLM
    except (URLError, HTTPError, KeyError, ValueError, TimeoutError, OSError) as exc:
        result = _offline_generate(...)  # 回退
        fallback_note = f"大模型调用失败（{type(exc).__name__}），已自动回退到离线规则引擎。"
else:
    result = _offline_generate(...)
```

回退提示会追加到 `notes` 里，B 端生成结果页能直接看到「为什么这次是规则引擎生成的」。

**大模型分支的实现**（`_llm_generate()`）：

- System Prompt 用 `LLM_SYSTEM_PROMPT` 硬约束四件事：① 不得编造地名/文物/史实；② 语言面向儿童、句子短；③ 任务必须是现场可执行的动作；④ 只输出 JSON；
- User Prompt 携带景区名与坐标、生成模式、年龄层、剧情风格、剧本标题、章节数、节点数，以及**最多 60 条景区素材**（每条截断 160 字）；
- 请求体带 `temperature: 0.7`、`response_format: {"type": "json_object"}`；
- 返回后剥离 ``` 代码围栏再 `json.loads`，并为任务补齐 `type_label` / `target_count` / `reward_growth` / `age_band`。

### 4.6 `parent.py` 家长模式引擎

对应商业计划书 P04 的家长痛点。两个原型都没有家长界面，这是本项目从痛点推导出的新能力。
文件只导出 4 个函数，**全部由数据库真实记录推导，不编造数字**。

| 函数 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `family_summary(user_id)` | 用户 id | `child` / `device` / `next_level` / `overview` / `growth` / `growth_note` / `weekly` / `badges_recent` / `scenarios` / `suggestions` | 家庭成长概览 |
| `trip_report(user_id, scenario_id)` | 用户 id + 剧本 id | `scenario` / `summary` / `chapters` / `trail` / `growth_gain` / `badges` / `knowledge` / `questions` | 单次旅行报告 |
| `scenario_reports(user_id)` | 用户 id | 可查看报告的剧本列表 | 报告列表页 |
| `_weekly_activity` / `_growth_note` / `_knowledge_for` / `_questions_for` | 内部辅助 | — | 见下 |

**① 概览的 6 项指标口径**（`family_summary`）

| key | 口径 SQL 要点 | `of`（上限） |
|---|---|---|
| `cities` | `COUNT(DISTINCT s.park_id)` from `progress ⋈ scenarios` | 景区总数 12 |
| `stories` | `COUNT(*) FROM progress WHERE status='done'` | **非草稿**剧本数（当前 7） |
| `nodes` | `COUNT(*) FROM node_visits WHERE user_id=?` | 节点总数 51 |
| `tasks` | `COUNT(DISTINCT task_id) FROM task_submissions WHERE passed=1` | `null`（无上限） |
| `badges` | `COUNT(*) FROM user_badges` | 徽章总数 24 |
| `minutes` | `SUM(tasks.avg_minutes)` over 去重后的已通过任务；无记录时 `12 × tasks_done` | `null` |

> 注意 `stories.of` 用的是 `status != 'draft'`，而**不是**全部剧本数——
> 草稿剧本孩子根本进不去，拿它当分母会让「完成度」永远显得偏低。

**② 五维画像解读**（`_growth_note`）

```
top = 五维最大值所对应的维度；low = 最小值
spread = top - low
spread <= 15 → 「很均衡」
spread >= 30 → 「偏向明显」
否则         → 「比较自然」
输出：「孩子在「{top}」上表现最突出（{top值}），「{low}」相对最少（{low值}），整体发展{tone}。」
```

真实输出：`孩子在「观察」上表现最突出（85），「创造」相对最少（62），整体发展比较自然。`

**③ 亲子建议的规则来源**（按顺序各取一条，最多 4 条）

| 顺序 | 来源 | 真实输出 |
|---|---|---|
| 1–2 | 五维中**最低的两项** → 查 `DIM_ADVICE` 固定话术 | 「创造」还有提升空间 · 「勇气」还有提升空间 |
| 3 | `parks.lit = 0` 且**有非草稿剧本**的景区，按 `sort_order` 取第一个 | 下一站可以去云南 ——《雨林寻踪》的剧本已经准备好了 |
| 4 | `badges.scenario_id` 指向 `status='online'` 剧本、且用户尚未获得，按 `sort_order` 取第一枚 | 再完成一个剧本就能拿到「雨林探险家」 |

`DIM_ADVICE` 是 5 条写死但具体的陪玩方法（探索 / 创造 / 观察 / 知识 / 勇气各一条），
例如「创造」→「鼓励孩子把旅途中看到的东西画下来、讲出来，或者自己编一个后续剧情。」

**④ 知识点反查**（`_knowledge_for`，家长模式的价值核心）

把「孩子实际走过的路」映射回「景区里真实的资料」，两级退化策略：

```
for node in 已到访节点:
    place = node.place                      # 如「大雁塔」「钟楼」
    ① 主路径：SELECT * FROM materials
              WHERE park_id = ? AND status='indexed'
                AND (title LIKE '%place%' OR tags LIKE '%place%')
              ORDER BY LENGTH(content) ASC LIMIT 1
    ② 退化： 从 node.story_text 抽一个 2–4 字中文关键词（去掉「阿游/我们/什么…」停用词）
              再 WHERE content LIKE '%关键词%'
    命中 → 取素材前两句（≤120 字）作为「知识点」，标注来源节点；同一 material_id 只出现一次
最多 6 条
```

真实输出（可复现）：

| 来源节点 | 反查到的素材 | 分类 |
|---|---|---|
| 抵达大雁塔 | 大雁塔塔影的传说 | 民间传说 |
| 大唐不夜城 · 铜钱线索 | 大唐不夜城步行街路线 | 景区地理 |
| 钟楼 · 时空回响 | 钟楼与城墙的空间关系 | 景区地理 |

> `ORDER BY LENGTH(content) ASC` 是刻意选择：优先命中**短**素材，取前两句才不会变成一篇长文。
> 这条链路同时说明了产品闭环——`materials` 既是 AI 生成剧本的语料，也是家长报告的答案来源。

**⑤ 回家提问**（`_questions_for`，固定 3 条）

| # | 规则 | 用到的表 | 真实输出 |
|---|---|---|---|
| ① | 最近一次**通过**的任务 → 问是否还记得答案 | `task_submissions ⋈ tasks`（`ORDER BY submitted_at DESC LIMIT 1`） | 今天你完成了「找出塔身上 3 个特殊符号」，你还记得答案是什么吗？ |
| ② | **最后到访**的节点 → 问第一印象与新发现 | 传入的 `visited_nodes[-1]` | 在大雁塔，你第一眼注意到的是什么？有没有什么是后来才发现的？ |
| ③ | 该剧本所属景区素材库中**最短**的一条知识 → 让孩子复述给家长 | `materials ⋈ scenarios`（按 `scenario_id` 反查 `park_id`） | 考考你：关于「关中平原的地理形胜」，你能用自己的话讲给爸爸妈妈听吗？ |

第 ③ 条在素材缺失时退化为开放式想象题：「如果让你给这个故事编一个新结局，你会怎么编？」

**⑥ 两个容易踩的坑（已写进代码注释）**

1. **`task_submissions` 表没有 `scenario_id` 字段**——所有「按剧本归集」的查询
   （时间轴、成长累计、完成任务数、估算时长）都必须 `JOIN tasks t ON t.id = ts.task_id`
   再用 `t.scenario_id` 过滤。直接写 `WHERE ts.scenario_id = ?` 会直接报错。
2. **`events` 表没有 `user_id` 字段**——它是面向 B 端的运营动态流（`park_id` + 文案），
   不能用来统计「某个孩子的行为」。家长模式因此全部改用 `node_visits` 与
   `task_submissions`；`observability.business_counters()` 里也没有基于 `events` 的用户计数，
   而是用 `COUNT(DISTINCT user_id) FROM node_visits` 得到 `users_with_trail`。

## 7. 性能与工程实践

### 7.1 线程局部连接 + 短连接模型

`app/db.py`：

```python
_local = threading.local()

def get_conn():
    conn = getattr(_local, "conn", None)
    if conn is None:
        conn = sqlite3.connect(DB_FILE, check_same_thread=False)
        conn.row_factory = sqlite3.Row
        conn.execute("PRAGMA foreign_keys = ON")
        conn.execute("PRAGMA journal_mode = WAL")
        _local.conn = conn
    return conn
```

- **每个线程一个连接**（懒创建），避免 `sqlite3` 跨线程报错，也避免每请求新建连接的握手开销；
- `row_factory = sqlite3.Row` 之后统一 `dict(row)`，接口层可直接 JSON 序列化；
- 写操作 `execute()` 内部 `commit()`，读操作用完即关游标；
- 所有 SQL 都走参数绑定（不拼接用户输入），`insert/update` 由 dict 生成列名与占位符。

### 7.2 WAL 模式

`PRAGMA journal_mode = WAL` 让读操作不被写操作阻塞。对本项目的实际意义：B 端后台在看板轮询统计的同一时刻，C 端仍能提交任务（`task_submissions` 写入），两者不会互相阻塞。

### 7.3 索引清单（`app/schema.sql` 真实定义，共 8 个）

```sql
CREATE INDEX IF NOT EXISTS idx_nodes_scenario   ON nodes (scenario_id, idx);
CREATE INDEX IF NOT EXISTS idx_tasks_node        ON tasks (node_id);
CREATE INDEX IF NOT EXISTS idx_tasks_scenario    ON tasks (scenario_id);
CREATE INDEX IF NOT EXISTS idx_chapters_scenario ON chapters (scenario_id, idx);
CREATE INDEX IF NOT EXISTS idx_materials_park    ON materials (park_id, category);
CREATE INDEX IF NOT EXISTS idx_visits_user       ON node_visits (user_id);
CREATE INDEX IF NOT EXISTS idx_subs_user         ON task_submissions (user_id, task_id);
CREATE INDEX IF NOT EXISTS idx_events_park       ON events (park_id, id);
```

对应的热点查询：

| 索引 | 服务的查询 |
|---|---|
| `idx_nodes_scenario` | `ORDER BY idx` 的节点链（顺序解锁、剧情详情、画布） |
| `idx_tasks_node` | 节点下的任务（`node_is_done`、节点任务列表） |
| `idx_tasks_scenario` | 按剧本聚合任务状态（`node_status_chain`） |
| `idx_chapters_scenario` | 章节按 `idx` 排序 |
| `idx_materials_park` | 素材库按景区+分类计数、AI 生成读取素材 |
| `idx_visits_user` | 用户到访集合（状态推导、进度刷新） |
| `idx_subs_user` | 计数型任务进度累计 |
| `idx_events_park` | 后台实时动态按景区+时间倒序 |

### 7.4 为什么用 `DROP TABLE` 而不是删库文件

`db.init_db(force=True)` 的注释写得很直白：

> 不能直接删除 `.db` 文件——服务运行时 WAL 文件被占用，删除会失败并导致「表已存在但数据未清空」。因此统一用 `DROP TABLE`。

实现上先 `PRAGMA foreign_keys = OFF`，再从 `sqlite_master` 读出所有非 `sqlite_%` 的表逐个 `DROP TABLE IF EXISTS`，最后恢复 `PRAGMA foreign_keys = ON`，再 `executescript(schema.sql)` 重建。这样：

- 不依赖文件系统权限；
- 在服务运行中也能安全重播（`python run.py --reseed`）；
- `schema.sql` 始终是唯一的结构来源。

## 8. 可观测性

实现位置：`app/observability.py`（约 130 行）+ `app/main.py` 的一个 HTTP 中间件。
目标是在**不引入任何外部依赖**（无 Prometheus / 无日志库）的前提下，让这个本地工具
「出问题能查、跑得慢能看见」。

### 8.1 结构化请求日志

```
[游伴] GET     /api/c/home                                   200  41.5ms
[游伴] POST    /api/c/task/12/submit                         200   8.2ms
[游伴] GET     /api/c/task/999                               404   1.1ms
```

- 一行一条，`method` 左对齐 7 位、`path` 左对齐 44 位、`status` 左对齐 4 位、耗时右对齐 7 位带 `ms`，
  便于 `grep`/`awk` 直接切片。
- **静态资源不刷屏**：`QUIET_PREFIXES = ("/c/", "/admin/", "/favicon")` 与门户 `/` 不打印日志
  （`observability.should_log()`），但**仍然计入指标**。
- 500 异常单独记录：中间件的 `except` 分支先记 `500` 再 `raise`，保证异常请求不丢指标。

### 8.2 请求指标与路径归一化

指标是**进程内**的 `defaultdict`，结构 `"METHOD path" -> {count, total_ms, max_ms, errors, slow}`，
另有一个长度上限 50 的 `_recent` 环形列表，全部操作用 `threading.Lock` 保护。

关键点是**路径归一化**（`app/main.py::_normalize`）：

```python
_ID_SEGMENT = re.compile(r"/\d+")
def _normalize(path: str) -> str:
    return _ID_SEGMENT.sub("/{id}", path)      # /api/c/task/12 -> /api/c/task/{id}
```

不归一化的话，每个任务 id 都会变成一个独立端点，指标会被打成碎片、完全无法聚合。
归一化后真实结果是 **11 个端点**（如 `/api/c/task/{id}`、`/api/admin/scenarios/{id}`、
`/api/c/scenario/{id}`），一眼就能看出热点端点。

聚合快照（`snapshot()`）包含：

| 字段 | 含义 |
|---|---|
| `uptime_seconds` / `requests_total` / `errors_total` / `error_rate` | 进程维度汇总 |
| `avg_ms` | 全局平均耗时 |
| `slow_threshold_ms` | 慢请求阈值，常量 `SLOW_MS = 300.0` |
| `endpoints[]` | 按 `count` 降序的端点明细（`count` / `avg_ms` / `max_ms` / `errors` / `slow`） |
| `slowest[]` | 按 `max_ms` 降序的前 5 名 |
| `recent[]` | 最近 20 条请求明细（时间 / 方法 / 路径 / 状态 / 耗时） |

### 8.3 业务计数

`business_counters()` 全部**实时查库**（不缓存、不落表），共 21 个计数：

| 类别 | 计数项 |
|---|---|
| 内容规模 | `parks` / `parks_lit` / `scenarios` / `scenarios_online` / `nodes` / `tasks` / `materials_indexed` |
| 用户与设备 | `users` / `devices_activated` / `codes_used` / `users_with_trail` |
| 行为量 | `node_visits` / `task_submissions` / `tasks_passed` / `task_pass_rate` / `badges_granted` / `growth_total` / `events_logged` |
| AI | `ai_jobs` / `ai_scenarios_created` / `ai_avg_ms` |

> `users_with_trail` 用的是 `COUNT(DISTINCT user_id) FROM node_visits`，
> **不是** `events` 表——`events` 没有 `user_id` 字段（见 4.6 节的坑 ②）。

### 8.4 两个查询入口与响应头

| 入口 | 用途 |
|---|---|
| `GET /api/admin/observability` | B 端后台「运行指标」，给人看 |
| `GET /api/metrics` | 系统命名空间下，给脚本巡检用（内容等价） |
| `GET /health` | 除 `ok` / `db` / `version` 外，额外返回 `uptime_seconds` / `requests_total` / `avg_ms` / `error_rate` |

每个响应都带 **`X-Response-Time`** 头（如 `41.5ms`），可直接在浏览器 Network 面板逐条观察，
不需要打开任何监控面板。

### 8.5 为什么把指标放在内存里

- 定位是**本地演示工具**：无外部监控依赖 = 拿到就能跑，不会有「连不上 Prometheus 就启动失败」的问题；
- 代价是**服务重启即清零**。这被明确写进了接口文档（`API.md` 2.21 的 `note` 字段），
  且业务计数部分因为实时查库而**不受重启影响**——两类数据各司其职：
  请求指标回答「这次运行健不健康」，业务计数回答「这份数据是什么状态」。

### 8.6 顺带踩到的一个 Windows 坑（端口探测）

`run.py` 与 `tests/run_all.py` 都用同一个 `port_is_free()` 探测空闲端口。
它在 Windows 上**刻意不设置 `SO_REUSEADDR`**：

```python
def port_is_free(host: str, port: int) -> bool:
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
        # 注意：不设 SO_REUSEADDR
        try:
            s.bind((host, port))
            return True
        except OSError:
            return False
```

Windows 的 `SO_REUSEADDR` 允许绑定到**已被占用**的端口（语义与 Linux 不同，Linux 上用于
快速重用 TIME_WAIT 状态的端口）。一旦设置，探测会**永远返回「可用」**，
而 uvicorn 随后以独占方式绑定失败并报 `WinError 10048`。
这个坑在本机表现为「探测说 8770 空闲 → 启动却失败」，由 `tests/port_check.py` 守护。
